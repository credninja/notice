1. End-to-End Pipeline Overview

NOTICE ingests raw network traffic through Suricata, persists alerts into an indexed SQLite database, enriches them with threat intelligence and kill-chain classification, promotes qualifying alerts into analyst-managed incidents, and exposes everything through a real-time web UI. The entire flow runs on a single host with no external dependencies beyond optional VirusTotal / AbuseIPDB API keys.

2. Data Flow — Six Layers

1Capture Layer (Suricata)

  • Two interfaces: enp0s3 (local traffic) + enp0s8 (mirror port)
  • ~1,500 detection rules including 35 custom NOTICE rules (SID 1000000–1000799)
  • Rule categories: brute force, port scans, C2 beaconing, malware, MITM, lateral movement
  • Output format: EVE JSON (one JSON object per line)

2Ingestion Layer (pipeline.py)

  • Runs as daemon thread inside app.py
  • Tails eve.json every 2 seconds
  • Byte-offset bookmark in pipeline_state table survives restarts
  • Detects log rotation via inode change; detects truncation via offset > file size
  • Only event_type=alert events get inserted (flow / dns / http events skipped for performance)

3Storage Layer (SQLite WAL mode)

TablePurposeTypical size
ingested_alertsAll Suricata alerts, indexed by ts/sid/src/dst146K+ rows
incidentsAnalyst-managed cases23K+ rows
assetsPassive network discoveryhundreds
evidenceFile metadata + SHA256per-incident
cacheAPI response cache with TTLKB range

4Enrichment Layer (Analyzers)

  • Correlation: groups alerts into kill chain phases (Recon → Exploitation → C2 → Actions)
  • Threat Intel Queue: fetches VirusTotal + AbuseIPDB for external IPs (rate-limited)
  • GeoIP: MaxMind lookup for country / ISP / org
  • Auto-Promotion: rules that automatically create incidents (severity + IOC threshold + burst detection)

5API Layer (Bottle + WSGI)

  • HTTPS on port 8080 (self-signed cert)
  • Cookie-based session auth (notice_session)
  • RBAC: admin / analyst / viewer roles
  • API keys for programmatic access
  • Server-sent events (SSE) for live alert stream
  • 2-minute response cache for expensive queries

6Presentation Layer (Vanilla JS SPA)

  • Single-page app, no framework (pure JS + D3 + Chart.js)
  • Real-time updates via SSE stream
  • Grouped alert view (deduplicated by SID+src+dst)
  • On-demand PCAP retrieval, incident promotion, evidence upload

4. Resilience Features

  • Bookmark persistence — pipeline restart resumes from last processed byte
  • Log rotation detection — inode change OR truncation resets bookmark
  • Connection pool with busy_timeout=30000 (SQLite WAL)
  • Auto-reconnect — server survives Suricata restart
  • Cache-first TI lookups — avoid API rate limits

5. Correlation Engine

Step 1: Signature → Kill Chain Phase Mapping

Each Suricata rule name gets fuzzy-matched against a SIGNATURE_MAP (100+ patterns) to assign it a kill chain phase AND a MITRE ATT&CK technique:

SIGNATURE_MAP = [
    {"pattern": "scan",         "phase": 1, "phase_name": "Reconnaissance",
     "tactic": "TA0043", "technique": "T1046"},
    {"pattern": "brute",        "phase": 4, "phase_name": "Exploitation",
     "tactic": "TA0006", "technique": "T1110"},
    {"pattern": "sql injection","phase": 4, "phase_name": "Exploitation",
     "tactic": "TA0002", "technique": "T1190"},
    {"pattern": "webshell",     "phase": 5, "phase_name": "Installation",
     "tactic": "TA0003", "technique": "T1505.003"},
    {"pattern": "beacon",       "phase": 6, "phase_name": "Command & Control",
     "tactic": "TA0011", "technique": "T1071.001"},
    {"pattern": "exfil",        "phase": 7, "phase_name": "Actions on Objectives",
     "tactic": "TA0010", "technique": "T1048"},
]
Example: NOTICE LATERAL SSH Brute Force matches pattern "brute" → Phase 4 Exploitation, MITRE T1110 Brute Force.

Step 2: Group Alerts by (attacker, victim) Pair

pairs = defaultdict(lambda: {"alerts":[], "phases_seen":set(), ...})
for ev in iter_events(event_types={"alert"}, minutes=minutes):
    key = (src_ip, dst_ip)
    pairs[key]["alerts"].append(alert_data)
    pairs[key]["phases_seen"].add(phase)

Every alert between the same source and destination gets bundled together into one "attacker → victim" pair.

Step 3: Chain Detection — Multi-Phase = Real Attack

real_phases = pair["phases_seen"] - {0}   # exclude unmapped
if len(real_phases) < 2 and len(pair["signatures"]) < 3:
    continue  # not an attack chain, just noise

Need either 2+ different phases OR 3+ unique signatures in the same phase to qualify as an attack chain.

Step 4: Severity Escalation Rules

has_exploitation = 4 in real_phases    # brute force, SQLi, RCE
has_c2           = 6 in real_phases    # beacon, cobalt strike
has_exfil        = 7 in real_phases    # data exfil, DNS tunnel

if has_exploitation and (has_c2 or has_exfil):
    chain_severity = "critical"   # full kill chain observed
elif has_exploitation:
    chain_severity = "high"       # attacker got in
elif max_phase >= 4:
    chain_severity = "high"
else:
    chain_severity = "medium"     # just recon
A chain going Recon → Exploitation → C2 gets marked critical automatically.

6. Auto-Promotion Engine

File: analyzers/auto_promote.py

Runs as a daemon thread every N minutes. Evaluates the last window of alerts against user-defined rules stored in auto_promote_rules table.

Four Criteria Types

CriterionBehavior
ti_maliciousAlert's external IP has TI score ≥ threshold (VT + AbuseIPDB, cache-only)
alert_burstSame (sid, src_ip) fired ≥ threshold times in window
killchain_phaseSignature maps to phase ≥ threshold (e.g., ≥ 4 = exploitation)
critical_assetAlert touches an asset marked business_critical=1

Idempotency Guard (Prevents Duplicates)

existing = conn.execute(
    "SELECT id FROM incidents WHERE signature_id=? AND attacker_ip=? "
    "AND victim_ip=? AND created_at > datetime('now','-1 day') "
    "ORDER BY id DESC LIMIT 1",
    (sid, src, dst),
).fetchone()
if existing:
    return existing["id"]   # already promoted, don't create duplicate

Same (SID, src, dst) within 24 hours = returns existing incident. This is why re-running the sweeper is safe.

Auto-Seeded IOCs

When promotion happens, the incident gets IOCs auto-attached:

seed_iocs = [
    ("src_ip", src),
    ("dest_ip", dst),
    ("signature_id", sid),
    ("signature", sig),
]

These are the "primary" IOCs. Additional auxiliary IOCs get added by the clustering engine (external IPs from related alerts, recurring SIDs, etc.).

Full Audit Trail

Every decision — promoted, skipped, failed — is logged to auto_promote_decisions:

CREATE TABLE auto_promote_decisions (
    rule_id, rule_name, signature_id, src_ip, dest_ip,
    decision,      -- 'promoted' | 'skipped' | 'failed'
    reason,        -- e.g., "burst threshold 5 not met (count=3)"
    incident_id    -- if promoted
)

You can query the DB directly and see exactly why each alert did or didn't become an incident.

Upload Flow

@app.post("/api/incidents/<id>/evidence")
def upload_evidence(incident_id):
    # 1. Size check (50 MB max)
    if len(file_data) > MAX_EVIDENCE_SIZE:
        return {"error": "File exceeds 50MB"}

    # 2. Compute SHA256 (chain of custody hash)
    h = hashlib.sha256()
    h.update(file_data)
    sha = h.hexdigest()

    # 3. Deduplicated filename (adds -1, -2 if collision)
    save_path = _unique_filename(incident_dir, filename)

    # 4. Write to disk
    with open(save_path, "wb") as f:
        f.write(file_data)

    # 5. Insert DB metadata
    conn.execute("""INSERT INTO evidence
        (incident_id, filename, file_path, file_size, mime_type,
         description, hash_sha256, uploaded_by, uploaded_at)
        VALUES (?,?,?,?,?,?,?,?, datetime('now','localtime'))""", (...))

Why SHA256 Matters

The hash is stored in DB and shown in the report (sha256:9619954b3f69e283…). If someone tampers with the file on disk, the SHA256 in the DB won't match — proving chain of custody was broken. This is what makes evidence admissible for compliance / legal proceedings.

8. Real-World Example — SSH Brute Force End-to-End

Walk-through of the SSH brute force test performed on 2026-07-29:

#StageWhat happens
1 Detection Suricata sees 3 SYN packets from 10.2.139.119 → 10.1.96.53:22 within 120s → fires SID 1000701 alert
2 Ingestion pipeline.py picks it up from eve.json in ≤ 2s → inserts into ingested_alerts
3 Classification Correlation engine maps signature "SSH Brute Force" → "brute" pattern → Phase 4 Exploitation, MITRE T1110
4 Promotion Auto-promote checks rules: killchain_phase criterion, threshold=4 → MATCHES; severity check: alert.severity=1 (critical) → passes floor; creates Incident #23065 with auto-seeded IOCs
5 Evidence Analyst investigates → attaches a screenshot as evidence; SHA256 computed, stored on disk + DB
6 Reporting Analyst marks TP + closes with RCA; daily CSV/PDF report includes: investigation summary, root cause, attached screenshot filename + SHA256

Every step is auditable (audit_log + auto_promote_decisions), idempotent (24-hour incident dedup), and survives restarts (byte-offset bookmark). That's the whole flow.
